The problem

Information overload outgrew our tools

Direct search is rigid, classic filters are opaque, recommenders erase your agency. The three richer mechanisms that do help — faceted filtering, navigation between related collections and set operations — exist only in isolation.

Our goal: a single, domain-agnostic engine that unifies the three as primitives of one calculus.

Under the hood

Every action is an operation on a formal state

A state is a tuple ⟨ c, F⁺, F⁻, R⁺, R⁻, L ⟩ — active collection, metadata & reference filters, and a history of links. Filtering, link, goback and union are defined operations with precise semantics.

The model is the reusable contribution — decoupled from the language and from any catalog.

  • Java 17 Servlets on Tomcat 10 — direct HTTP control, no heavyweight framework.
  • RESTful API exposes the engine; one endpoint per resource, one for all actions.
  • The middle three layers live inside Apache Tomcat.
Two key decisions

Stateful by design · state → SQL

  • Exploration is cumulative, so REST's stateless model fights us. We keep a StateManager in the HTTP session.
  • No intermediate result sets are materialized: on each request the state is translated into one parameterized SQL query.
  • Links become recursive nested sub-queries — the formal semantics, executable.
-- one filter → one EXISTS clause AND EXISTS (SELECT 1 FROM metadata m WHERE m.entity_id = e.global_id AND m.key = ? AND m.value = ?) -- exclusion → NOT EXISTS · link → IN (SELECT …)

Conclusions & future work

Three mechanisms, one calculus

What we delivered

  • An engine that unifies filtering, navigation and union.
  • A formal model — the most reusable contribution.
  • Validated on two real, structurally different catalogs.

Where it goes next

  • LLM assistance over visible operations (agency kept).
  • Distribution across nodes; incremental query generation.
  • New domains, multi-value selection, user persistence.
